## 1. 项目概述

### 1.1 项目简介

**变电站巡检仿真系统**是一个多进程 Java 仿真平台，模拟多台小车在二维网格地图上协作探索变电站环境。小车需要避开障碍物和不可达区域，通过智能路径规划（BFS / A*）与目标分配（贪心前沿探索）尽可能覆盖地图上全部可达格子。

系统整体采用**黑板架构（Blackboard Architecture Pattern）**：Redis 作为共享黑板存放地图状态与车辆信息，RabbitMQ 作为消息总线在模块间传递命令与事件。Controller 模块充当唯一的调度节点，以固定节拍（tick）驱动整车群状态机运转。

### 1.2 核心指标

| 指标 | 默认值 | 可配置范围 |
|------|--------|-----------|
| 地图尺寸 | 30×30 格 | 10×10 ~ 100×100 |
| 车辆数量 | 5 台 | 1~10，支持运行时 ADD_CAR 动态添加 |
| 障碍物比例 | 15% | 0~50% |
| 节拍间隔 | 500ms | 100ms~2000ms |
| 路径算法 | BFS（广度优先）/ ASTAR（A* 寻路） | — |
| 状态机 | 5 态（IDLE / WAITING_ROUTE / READY / MOVING / BLOCKED） | — |

### 1.3 项目模块总览（全部 9 个模块）

| 序号 | Maven artifactId | 模块名 | 入口类 | 进程角色 |
|------|-----------------|--------|--------|----------|
| 1 | `common` | 公共库 | — | 公共库（model / mq / redis / auth / sql / map / analysis / replay） |
| 2 | `controller` | 调度大脑 | `ControllerMain` | **唯一调度者**：按 tick 驱动状态机 |
| 3 | `car` | 小车执行端 | `CarMain` | **执行端**（多实例，每车一进程/线程） |
| 4 | `navigator` | 路径规划 | `NavigatorMain` | **知识源**：BFS / A* 寻路 |

## 4. 架构设计

### 4.1 架构模式：黑板架构 (Blackboard Architecture)

系统采用黑板架构模式的三个核心要素：

1. **黑板 (Blackboard)** -- Redis 实例，存放所有共享数据  
2. **知识源 (Knowledge Sources)** -- 各业务模块：TargetPlanner、Navigator、StrategySupervisor、Car  
3. **调度器 (Controller)** -- 唯一的控制器，按固定节拍驱动知识源

**关键约束**（架构纪律）：
- 知识源之间**不允许直接通信**，必须通过 Controller 中转
- 知识源之间通过 Redis 黑板共享数据，**不直接读写彼此的模块内状态**
- Controller 是唯一调度者，其他模块仅响应 Controller 发出的 MQ 消息

### 4.2 模块依赖关系

```
                    ┌──────────────┐
                    │   common     │  (公共库：model、mq、redis、auth、sql、map、analysis、replay、infra)
                    └──────┬───────┘
           ┌───────────────┼───────────────────────────────┐
    ┌──────┴──────┐  ┌────┴────┐  ┌──────┴──────┐  ┌─────┴──────┐
    │  controller │  │   car   │  │  navigator  │  │  display   │
    └─────────────┘  └─────────┘  └─────────────┘  └────────────┘
    ┌──────────────┐  ┌─────────────────┐  ┌───────────────────┐
    │target-planner│  │task-configurator│  │strategy-supervisor│
    └──────────────┘  └─────────────────┘  └───────────────────┘
                              ┌──────────┐
                              │ launcher │ (聚合启动，仅依赖各模块)
                              └──────────┘
```

- 所有业务模块**仅依赖 common**，互不依赖
- Launcher 依赖所有业务模块（聚合式一键启动）

### 4.3 组件交互总览

### 4.4 架构关键属性

| 属性 | 实现方式 |
|------|----------|
| **解耦** | 模块间仅通过 MQ 消息类型交互，不直接调用 |
| **共享状态** | Redis 黑板：地图位图、车辆位置/目标/路径/状态、配置 |
| **单调度者** | Controller 是唯一 Schedule 驱动者，避免并发调度冲突 |
| **位置安全** | Redis 分布式锁 (`lock:CarID`) + 位置预约锁 (`pos:reserve:{row}:{col}`) |
| **单实例控制** | Controller 通过 `controller:instance` 锁（SET NX EX）防止多实例 |
| **分布式** | 各模块可部署在不同机器，通过 CLI 参数覆盖 Redis/MQ 地址 |
| **可扩展** | 新增知识源仅需在 Controller 中声明其 MQ 队列并添加入口回调 |

## 5. 核心组件

### 5.1 Controller（调度大脑） -- 模块 1/9

**Maven artifactId**：`controller`  
**入口**：`ControllerMain.main(args)`  
**职责**：系统唯一调度器，按固定节拍驱动整车群状态机。

#### 核心类

| 类 | 职责 |
|---|------|
| `ControllerMain` | 初始化 Redis/MQ、声明所有队列、注册关闭钩子、启动监听 |
| `TickScheduler` | 基于 ScheduledExecutorService 的定时节拍器，支持暂停/恢复/调速 |
| `StatusDispatcher` | 核心状态机：发现车辆 → 遍历状态 → 分派 ASSIGN_TARGET / PLAN_ROUTE / TICK_MOVE / SUPERVISE_ROUTE → 广播 REFRESH_ALL |
| `CommandHandler` | 入站消息路由器：TASK_READY / TARGET_ASSIGNED / ROUTE_PLANNED / MOVED / BLOCKED / TOGGLE_PAUSE / SET_TICK_INTERVAL ... |

#### 状态分派逻辑（每 tick 执行）

```
StatusDispatcher.dispatch():
  1. tick++  // 节拍递增
  2. if 探索率 >= 100% 且无未探索格子 → completeTask()
  3. 扫描 Redis Car*:Status 发现所有活跃车辆
  4. 逐车按状态分发：
     IDLE          → 发送 ASSIGN_TARGET 到 TargetPlannerCmd
     WAITING_ROUTE → 发送 PLAN_ROUTE 到 NavigatorCmd
     MOVING        → 检查是否卡住 (MOVING_STUCK_TICKS=2)
     BLOCKED       → 检查阻塞超时 (随机2~5 tick)
     READY         → 留在第二轮统一发送 TICK_MOVE
  5. 所有 READY 车发送 TICK_MOVE 到 Car_{carId} 队列
  6. 广播 REFRESH_ALL 到 UpdateView fanout exchange
  7. 辅助判定：全车 IDLE 且无 pending 请求持续 30 tick → 强制完成
```

#### 关键常量

| 常量 | 值 | 说明 |
|------|-----|------|
| TICK 默认间隔 | 500ms | 可调 100~2000ms |
| 探索完成阈值 | 100% | 整数 100% |
| 全车 IDLE 超时 | 30 tick | 兜底完成判定 |
| 阻塞超时 | 2~5 tick | 随机阈值打破多车互堵死锁 |
| 移动卡住 | 2 tick | 连续 MOVING 超时强制切 READY |
| 等待路径超时 | 5 tick | 超时移除锁并回退 IDLE |
| 监督触发阈值 | 探索率 < 85% | 超过则不触发策略监督 |
| 监督冷却 | 15 tick | 同一车两次监督的最小间隔 |

### 5.2 Car（小车执行端） -- 模块 2/9

**Maven artifactId**：`car`  
**入口**：`CarMain.main(args)`（支持 `Car001` / `Car001 --dynamic` 两种模式）  
**可多实例**：每辆小车是一个独立进程（或 Launcher 中的独立线程）

#### 核心类

| 类 | 职责 |
|---|------|
| `CarMain` | 连接中间件 → 自注册（出生点选择）→ 订阅 Car_{carId} 队列 → 等待 TICK_MOVE |
| `CarAgent` | 消息分发：TICK_MOVE → MoveExecutor.executeMove / BLOCKED_TIMEOUT → 日志 |
| `MoveExecutor` | 原子移动执行：分布式锁 → 状态检查 → 位置预约 → 障碍检测 → pop 路径 → 更新位置 → 点亮地图 |

#### 自注册与出生点选择

```
selfRegister(BlackboardClient bb, carId, mapWidth, mapHeight, dynamicAdd):
  1. 动态模式 (--dynamic)：跳过 TaskConfigurator 等待，直接自初始化
  2. 预注册模式：轮询 200ms×25 次 (共 5s) 等待 TaskConfigurator 写入状态
  3. 若超时仍未注册 → 执行自初始化
  4. findSpawnPosition()：使用 SpawnPositionSelector 选择最优出生点
     - 避免障碍物 / 密封区 / 其他车位置 / 已探索区
     - 优先内部格（margin=1），无则放宽到边界
  5. 写入位置 → 初始化状态 IDLE → 点亮首格 + 热力图 + History
```

#### 移动执行流程 (executeMove)

```
executeMove(tick):
  1. 获取分布式锁 (lock:CarID)，失败则 skip 本拍
  2. 检查状态 == READY，否则 return
  3. 状态切为 MOVING（心跳）
  4. peek 下一步位置
  5. 位置预约锁 (pos:reserve:{x}:{y}, SET NX EX=3s)
     预约失败 → 计数卡住，≥3次切 BLOCKED
  6. 障碍物检查 → BLOCKED
  7. 其他车占据检查 → 卡住重试/BLOCKED
  8. pop 消耗该步 → 更新位置 → 点亮地图 + 热力图 + 步数/有效步数 + History
  9. 路径空了 → IDLE + 发 ROUTE_DONE
     还有路径 → READY + 发 MOVED
  10. 释放位置预约锁 + 分布式锁
```

#### 小车状态机（5 态）

| 状态 | 含义 | 写入者 | 前端颜色 |
|------|------|--------|----------|
| IDLE | 无目标/路径或行走完毕 | Controller, Car | #9E9E9E (灰) |
| WAITING_ROUTE | 已有目标，等待路径规划 | Controller | #FF9800 (橙) |
| READY | 有路径，等待本拍移动 | Controller, Car | #4CAF50 (绿) |
| MOVING | 本拍正在移动（心跳） | Car | #2196F3 (蓝) |
| BLOCKED | 下一步被阻挡 | Car | #F44336 (红) |

**纪律**：Car 不写 WAITING_ROUTE；Controller 不写 MOVING。

### 5.3 Navigator（路径规划） -- 模块 3/9

**Maven artifactId**：`navigator`  
**入口**：`NavigatorMain.main(args)`  
**订阅队列**：`NavigatorCmd`，消息类型 `PLAN_ROUTE`

#### 核心类

| 类 | 职责 |
|---|------|
| `NavigatorMain` | 连接中间件 → 声明队列 → 订阅 PLAN_ROUTE → 处理路径规划请求 |
| `PathPlannerFactory` | 根据算法名（BFS/ASTAR）创建对应 PathPlanner 实例 |
| `BfsPathFinder` | 广度优先搜索，保证最短路径 |
| `AStarPathFinder` | A* 启发式搜索，曼哈顿距离启发 |

#### 规划流程

```
handlePlanRoute(bb, bus, carId, algorithm, supervised, tick):
  1. 从 Redis 读取 carId:Position 和 carId:Target
  2. PathPlannerFactory.create(algorithm) 选择算法
  3. planner.plan(start, target, bb) 计算路径
     - 障碍物参考 mapBlock + 所有车当前位置（loadBlockedMapWithCars）
  4. 写前复查：车是否已移动（位置变化则放弃）
  5. bb.pushRoute(carId, route) 原子写入 RouteList
  6. 发送 ROUTE_PLANNED 消息到 ControllerCmd
```

### 5.4 TargetPlanner（目标分配） -- 模块 4/9

**Maven artifactId**：`target-planner`  
**入口**：`TargetPlannerMain.main(args)`  
**订阅队列**：`TargetPlannerCmd`，消息类型 `ASSIGN_TARGET`

#### 核心类

| 类 | 职责 |
|---|------|
| `TargetPlannerMain` | 连接中间件 → 声明队列 → 订阅 ASSIGN_TARGET → 调用 GreedyTargetAllocator |
| `GreedyTargetAllocator` | 贪心分配核心：按探索率分两阶段策略 |
| `TargetPathEstimator` | 快速 BFS 估算路径长度，用于多候选评分 |

#### 两阶段分配策略

**阶段一：探索率 < 85% -- 逐格前沿分配 (allocateByCell)**

1. `FrontierCellFinder.findFrontierCells()` 找出前沿格（已探索区边缘未探索格）
2. 若无前沿格 → 回退到全部未探索格
3. 排除已在此 tick 分配的目标（`alreadyAllocated` 集合同步）
4. 对每个候选格估算路径开销，综合得分：
   - `path.size()` 路径长度（越小越好）
   - `OVERLAP_PENALTY × overlap` 与别车路线重叠惩罚
   - `PERIMETER_TARGET_PENALTY` 贴边惩罚（避免沿外围兜圈）
   - `-CLUSTER_SIZE_WEIGHT × clusterSize` 附近未探索区域块越大越优先
   - `-UNEXPLORED_PATH_WEIGHT × unexploredPath` 路径经过未探索格越多越优先
   - `-INTERIOR_DEPTH_WEIGHT × depth` 越深入地图内部越优先

**阶段二：探索率 >= 85% -- 区域块分配 (allocateByCluster)**

1. `UnexploredClusterFinder.findClusters()` 将剩余未探索格聚类为区块
2. 对每个区块，选择前沿入口，综合评分（同上）
3. 写入 `carId:Target` → 发送 `TARGET_ASSIGNED`

### 5.5 StrategySupervisor（路线监督） -- 模块 5/9

**Maven artifactId**：`strategy-supervisor`（**新增模块**，v3 规划中不存在）  
**入口**：`StrategySupervisorMain.main(args)`  
**订阅队列**：`StrategySupervisorCmd`，消息类型 `SUPERVISE_ROUTE`

#### 核心类

| 类 | 职责 |
|---|------|
| `StrategySupervisorMain` | 订阅 SUPERVISE_ROUTE → 调用评估/优化 |
| `RouteEvaluator` | 评估路线质量：已探索格占比过高则返回 REPLAN |
| `RouteOverlapEvaluator` | 检测路线重合：多车行走相同未探索路径则请求重分配 |
| `WeightedPathPlanner` | 重新规划加权路径：偏好未探索格（已探索格代价高） |

#### 监督流程

```
handleSupervise(evaluator, overlapEvaluator, planner, carId, tick):
  1. 读取 carId:Position / carId:Target / RouteList / Status
  2. 状态非 READY → skip
  3. 重合检测：isHighlyOverlapped + 冷却期检查 → 清除路线/目标，发 overlapReassign
  4. evaluator.evaluate() → SKIP 则不做任何操作
  5. planner.plan() 计算加权新路线
  6. 新路线与旧路线相同或为空 → skip
  7. 新路线长度 > 旧长度 × 2.0 → skip（避免绕路过度）
  8. 复查车未移动 → pushRoute 原子写入新路线
  9. 发送 ROUTE_OPTIMIZED 消息到 ControllerCmd
```

### 6.4 认证与会话

## 8. 关键流程

### 8.1 完整仿真生命周期

```
用户点击「开始」→ Browser 发送 SET_CONFIG
  → Controller 收到 → forwardConfig → TaskConfigCmd
    → TaskConfigurator: selectiveClear → TaskInitializer.initialize
      → 写入 mapBlock / mapSealed / TaskConfig / 车辆出生点
      → 发送 TASK_READY → Controller
        → onTaskReady(): 激活 tick，声明车辆队列
          ┌→ TickScheduler 启动
          │
    ┌─────┴────── 每 tick 循环 ──────┐
    │                                │
    │  StatusDispatcher.dispatch()   │
    │  1. tick++                    │
    │  2. 发现所有车辆               │
    │  3. 逐车状态分派：            │
    │     IDLE → ASSIGN_TARGET      │
    │     WAITING_ROUTE → PLAN_ROUTE│
    │     READY → TICK_MOVE         │
    │     MOVING → 检查卡住          │
    │     BLOCKED → 检查超时         │
    │  4. 收到 ROUTE_PLANNED:       │
    │     可选 SUPERVISE_ROUTE      │
    │  5. 广播 REFRESH_ALL          │
    │                                │
    │  ┌→ TargetPlanner 分配目标    │
    │  │   TARGET_ASSIGNED → WAITING│
    │  │                             │
    │  ├→ Navigator 规划路径        │
    │  │   ROUTE_PLANNED → READY    │
    │  │                             │
    │  ├→ StrategySupervisor 审查   │
    │  │   ROUTE_OPTIMIZED → READY  │
    │  │                             │
    │  └→ Car 执行移动              │
    │      MOVED / ROUTE_DONE →     │
    │      DISPLAY 读取 Redis 推送  │
    │                                │
    └──────── 循环直至完成 ──────────┘
    │
  ↓ 探索率 ≥ 100% 且无未探索格 → completeTask()
    → 停止 tick、冻结所有车辆、广播最终状态
    → 前端弹出保存窗口（localStorage + SQL 归档）
```

### 8.2 车辆状态转换流程

```
                    ┌─────────┐
         (初始) →   │  IDLE   │ ←──────────────────────────┐
                    └────┬────┘                            │
                         │ Controller: ASSIGN_TARGET        │
                         ↓                                  │
                  ┌──────────────┐                         │
                  │ WAITING_ROUTE│ (超时5 tick 回退 IDLE)   │
                  └──────┬───────┘                         │
                         │ Navigator: ROUTE_PLANNED          │
                         ↓                                  │
                    ┌────────┐                              │
                    │ READY  │ ←──────────────┐             │
                    └───┬────┘                 │             │
              ┌────────┼────────┐              │             │
              │        │        │              │             │
         TICK_MOVE   (监督)   (卡住)           │             │
              │        │        │              │             │
              ↓        ↓        │              │             │
         ┌──────┐ ┌──────┐     │              │             │
         │MOVING│ │等待监│     │              │             │
         └──┬───┘ │督完成│     │              │             │
            │     └──┬───┘     │              │             │
       ┌────┼────┐   │         │              │             │
       │    │    │   ↓         │              │             │
    MOVED  │  BLOCKED  ROUTE_OPTIMIZED        │             │
       │    │    │   └────→ READY             │             │
       │    │    │                            │             │
       │    │    └──→  Controller 处理         │             │
       │    │        超时清 Route/Target/      │             │
       │    │        BlockedTick → IDLE       │             │
       │    │                                 │             │
       ↓    ↓                                 │             │
   READY  ROUTE_DONE                          │             │
   (还有   → IDLE (路径走完) ─────────────────┘             │
   路径)                                                   │
                                                          │
           BLOCKED_TIMEOUT (Controller) ──────────────────┘
           (不常用，多数由 Controller 主动处理)
```

### 8.3 受阻恢复机制

```
Car 检测到阻塞:
  1. 清除 RouteList + Target
  2. 状态切 BLOCKED
  3. 记录 BlockedTick
  4. 发送 BLOCKED → Controller

Controller 收到 BLOCKED:
  1. onMoveAcknowledged (释放 TICK_MOVE 槽位)
  2. 下几个 tick 检测阻塞超时（随机 2~5 tick）
  3. 超时后：clearRoute + clearCarTarget + clearBlockedTick + 切回 IDLE
  4. 发送 BLOCKED_TIMEOUT 通知 Car
  5. 下一 tick：IDLE 触发 ASSIGN_TARGET → 重新分配目标
```

### 8.4 动态添加小车 (ADD_CAR)

```
用户点击「+ 添加小车」
  → Browser 发送 ADD_CAR → Display WebSocketBridge
    → resolveNextCarId(): 扫描现有车辆，分配下一个可用 CarId
    → 检查 car/target/car-1.0-SNAPSHOT.jar 是否存在
    → 检查进程是否已在运行
    → DynamicCarLauncher.launchAsync():
        java -jar car.jar Car00N --dynamic
    → CarMain 启动：连接 Redis/MQ → 自注册 → 选出生点 → 订阅队列
    → Display 收到进程就绪回调 → 广播 CAR_LAUNCHED → 刷新状态
```

### 8.5 初始化清键策略

**selectiveClear()** (替代旧 flushDB)：
1. DEL mapView, mapBlock, mapSealed, mapHeat, TaskConfig, explorationEvents
2. SCAN + DEL Car*:* 系列键（Position, Target, RouteList, Status, Steps, BlockedTick, History）
3. SCAN + DEL pos:reserve:* 和 lock:* 系列键
4. **保留** auth:session:*, auth:user_session:*, auth:kicked:*, auth:users 等认证键

### 9.3 分布式部署

通过 `deploy/infra.local.json` 配置文件或 CLI 参数覆盖，可将各模块部署在不同机器：

```json
{
  "redisHost": "192.168.1.101",
  "redisPort": 6379,
  "mqHost": "192.168.1.101",
  "mqPort": 5672,
  "role": "car",
  "displayHost": "192.168.1.104",
  "displayHttpPort": 8887,
  "displayWsPort": 8888,
  "cars": ["Car001", "Car002", "Car003"]
}
```

**典型分工**：
- Person A：Docker (Redis + RabbitMQ) + Controller
- Person B：Car × N（多进程）
- Person C：TaskConfigurator + Navigator + TargetPlanner + StrategySupervisor
- Person D：SQL Server + Display + 浏览器操作
